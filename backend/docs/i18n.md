# Internationalization

## Technology and ownership

The core uses Babel to parse and validate gettext PO catalogs, compile them in memory, apply
Unicode-aware plural rules, and format numbers and dates. This is one i18n stack; there is no
global dictionary or second translation framework.

Core owns only generic platform messages. Product copy belongs to the module that owns the feature:

    src/app/core/i18n/locales/{locale}/platform.po
    src/app/modules/{module}/locales/common/{locale}/messages.po
    src/app/modules/{module}/locales/bots/{bot_app_id}/{locale}/messages.po

There is no business module in the foundation, so only the core platform catalog is tracked. Tests
create temporary module catalogs to validate ownership and fallback behavior.

## Supported locales and resolution

The global supported locales are en, ru, and uz. Locale parsing validates and normalizes BCP 47
input:

    ru-RU -> ru
    en-US -> en
    uz-UZ -> uz
    uz-Latn-UZ -> uz-Latn

Unsupported locale tags are not treated as valid choices. The resolver falls back deterministically.

HTTP resolution order is:

1. authenticated user preference supplied by a future caller;
2. explicit request-level locale supplied by a future API contract;
3. valid bounded Accept-Language header;
4. global default locale.

Bot resolution order is:

1. explicit stored user preference supplied by the owning module;
2. explicit conversation or session locale supplied by the owning module;
3. provider language code;
4. bot app default locale;
5. global default locale.

HTTP middleware binds the resulting immutable Locale to the request context, emits Content-Language,
and resets the context after the response. Bot runtime constructs an immutable BotUpdateContext for
each update. Neither mechanism uses a mutable global locale.

## Scoped lookup and fallback

A module receives a ScopedLocalizer already bound to its module, translation domain, and optional
bot app. Normal module code supplies only semantic key, locale, and parameters. It cannot select
another module domain.

Lookup remains in one ownership scope:

    bot-app catalog for requested locale
      -> module common catalog for requested locale
      -> platform catalog only for platform.* keys
      -> same scopes for bot default locale
      -> same scopes for global default locale

There is no fallback to another module or bot app. A missing support message never resolves from a
sales catalog merely because the key has the same name.

Non-production missing keys raise a testable MissingTranslationError. Production emits a sanitized
structured warning and uses the generic platform temporary-unavailable message, never a raw key or
exception.

## Catalog conventions and validation

Use semantic dot-separated keys:

    start.welcome
    errors.temporary_unavailable
    language.changed
    commands.help.title

Do not use full source-language sentences, dynamic values, JSON property names, database keys,
metric labels, permissions, or error codes as translation keys.

PO catalogs are parsed with Babel at startup. Validation rejects missing catalog files, syntax
errors, duplicate msgid values, missing message strings, mismatched locale coverage, plural
contract differences, malformed placeholders, and placeholder mismatches across locales. Named
placeholders use only simple names such as {count}; attribute access, indexing, format expressions,
and missing parameters are rejected. User-supplied values are substituted only after validation.

Each module has one catalog root and translation domain. Startup also rejects an unregistered
directory below locales/bots, an invalid or unsupported locale directory, and conflicting domains
for one module root. A file-system addition therefore cannot silently widen translation scope.

Plural entries use gettext singular and plural IDs:

    msgid "messages.count"
    msgid_plural "messages.count_plural"
    msgstr[0] "You have {count} message"
    msgstr[1] "You have {count} messages"

Use locale-aware core helpers for number, currency, date, time, datetime, and percentage formatting.
Datetime formatting requires a timezone-aware value. Translation lookup and provider markup are
separate; bot output is plain text unless a future provider-specific renderer is explicitly added.

## Adding content or a locale

To add a module key, add it to every supported locale in the module common catalog or its bot-app
override catalog, preserve the exact placeholders, then run catalog and full test checks. To add a
bot-app override, add matching files below that app ID only; do not modify another bot's directory.

To add a locale, first update I18N__SUPPORTED_LOCALES and the intended app supported locales, then
add all required core, module common, and bot-app catalogs. Verify Babel plural forms, placeholder
parity, HTTP header resolution, bot fallback, and formatted output before enabling it in production.

Run from backend:

    make lint
    make typecheck
    make test-unit
    make test-smoke
    make test-architecture
    make test

The unit suite includes syntax, duplicate-key, placeholder, pluralization, coverage, and scoped
fallback checks. The smoke suite includes HTTP locale context and multi-app bot startup coverage.
